# R10 自主任务与定时任务协同规则草案

> 任务：阅读 `autonomous_operation_sop` 与 `scheduled_task_sop`，给出两类任务如何协同的简短说明文。  
> 报告路径：`./autonomous_reports/R10_自主任务与定时任务协同规则草案.md`

## 1. 基本模型对齐

### 1.1 自主任务（autonomous）

- 触发方式：  
  - 用户长时间离线（>30分钟）时由系统触发。  
  - 以 `./TODO.txt` 中**未完成条目**为任务池，每轮只取一条。  
- 目标定位：  
  - 偏「探索 / 规划 / 结构设计 / 工具试验」，强调**长期协作价值**与「训练数据覆盖不到」的部分。  
- 执行边界：  
  - 只读探测与 cwd 内写文件/脚本自由度较高。  
  - 修改 memory / 安装软件 / 外部 API 调用 等需要在报告中提议，等待用户审查。  
- 收尾三件事（缺一不可）：  
  1. 写报告 `./autonomous_reports/RXX_简短描述.md`。  
  2. 在 `./autonomous_reports/history.txt` 顶部 prepend 一条 `RXX | 日期 | 类型 | 主题 | 结论`。  
  3. 将 `./TODO.txt` 对应条目标记为 `[x]`。  

### 1.2 定时任务（scheduled）

- 触发方式：  
  - `reflect/scheduler.py` 每 60 秒轮询 `../sche_tasks/*.json`。  
  - 满足条件才触发：`enabled=true` + 当前时间 ≥ `schedule` + 冷却时间已过（基于 `../sche_tasks/done/` 最新报告时间戳）。  
- 任务定义：  
  - JSON 中只定义「**做什么**」：  
    ```json
    {"schedule":"08:00", "repeat":"daily", "enabled":true, "prompt":"..."}
    ```  
  - `repeat` 用于控制周期（daily / weekly / monthly / once / every_Nh / every_Nd）。  
- 报告路径：  
  - scheduler 在 prompt 中注入 `../sche_tasks/done/YYYY-MM-DD_任务名.md`。  
  - 执行完后**必须**将报告写入该路径，scheduler 以此判断「今天是否已执行」。  

## 2. 角色与优先级划分

### 2.1 角色差异

- 定时任务 =「计划内生产任务」  
  - 与具体日期/时间强耦合，强调**按时完成**。  
  - 报告路径和冷却逻辑都由 scheduler 控制，是「驱动型」。  

- 自主任务 =「闲时研究与改善」  
  - 利用用户离线时间和无定时任务压力的空档，做有长远价值的探索。  
  - 以 TODO 为任务池，是「机会型」。  

### 2.2 协同优先级原则

1. **定时任务优先于自主任务**  
   - 当收到 scheduler 发来的定时任务 prompt 时，应立即把当前自主任务视为「可中断」，优先完成定时任务。  
   - 自主任务进度通过 `update_working_checkpoint` 保留，任务本身不强制立刻收尾。  

2. **同一时间只聚焦一个「主」任务**  
   - 在单轮交互/调用内，同时处理多个定时任务或混合多个自主任务容易混乱。  
   - 规则：  
     - 若当前正执行定时任务：禁止在同一轮内自发开启新的自主任务。  
     - 若当前是自主任务轮次：如收到 scheduler 任务，应将自主任务状态写入 checkpoint 后，切换到定时任务。  

3. **报告命名与路径不得混用**  
   - 自主任务报告固定在 `./autonomous_reports/`，命名以 `RXX_...`。  
   - 定时任务报告必须写入 scheduler 注入的 `../sche_tasks/done/....md`，不得写到 autonomous 目录，也不要擅自改名。  

## 3. 协同操作细则（建议执行策略）

### 3.1 任务启动阶段

- 定时任务启动时：  
  1. 严格遵守 scheduled_task_sop：  
     - 第一件事：`update_working_checkpoint` 写清**报告目标路径**与任务目标。  
  2. 若当前有未完成自主任务：  
     - 不强行结算，但需在 checkpoint 中明确「当前切换到定时任务，待空闲再继续 RXX」。  

- 自主任务启动时（用户离线触发）：  
  1. 先检查是否有正在进行的定时任务（通常通过当前 prompt 内容可判断）：  
     - 如 prompt 指向 `../sche_tasks/done/...`，说明这是定时任务，此轮应该视为定时任务，不再开启 autonomous。  
  2. 若是纯 AUTO prompt（当前这种）：  
     - 按 autonomous SOP：  
       - 先读 `./TODO.txt`，选一条未完成、且类型不与上一轮重复的任务；  
       - 写 `update_working_checkpoint` 记录新 RXX 自主任务的报告路径与 TODO 行号。  

### 3.2 执行过程中的切换

- 情景：自主任务执行中，下一轮突然收到 scheduler 定时任务 prompt。  
  - 行为建议：  
    1. 不必立即写 autonomous 收尾报告，但要在下一次继续该自主任务前**重读 autonomous_operation_sop** 确认状态。  
    2. 当前轮直接当作定时任务处理：  
       - 用 `update_working_checkpoint` 记录定时任务关键参数（报告路径、任务名）。  
       - 按照定时任务要求执行，写好 `../sche_tasks/done/...md` 报告。  
    3. 定时任务完成后，才恢复处理原自主任务。  

- 情景：短时间内 scheduler 触发多个定时任务 JSON。  
  - 行为建议：  
    - 严格「**一轮一个定时任务**」：每轮只执行、汇报一个 JSON 任务。  
    - done 报告写完后，如 scheduler 再次下发其它任务，再按新 prompt 单独执行。  

### 3.3 资源与副作用控制

- 文件与目录约束：  
  - 自主任务：  
    - 正常情况下只在 cwd（`./`）及其子目录中写文件。  
    - 修改 `../memory` 仅能通过 `file_patch`，并应在 autonomous 报告中明确说明改动动机（通常建议先提议，待用户批准）。  
  - 定时任务：  
    - 遵守其 prompt 中明确的输入输出位置，不额外操作 `../memory`，除非任务内容明确要求。  

- 外部调用与安装：  
  - 两类任务对「外部 API / 安装软件」都有同样约束：  
    - 必须在报告中写成「建议」，等待用户审查决定是否执行，不得自发实施。  

## 4. TODO 与 history 的统一管理

### 4.1 自主任务的闭环

- autonomous 任务完成条件（对单个 RXX）：  
  1. 报告写入 `./autonomous_reports/RXX_*.md`；  
  2. `./autonomous_reports/history.txt` 顶部 prepend 对应记录；  
  3. `./TODO.txt` 中该行从 `[ ]` 改为 `[x]`。  

- 若任务因为定时任务打断尚未完成：  
  - 在再次恢复执行前，必须：  
    - 读一遍 autonomous SOP；  
    - 重新检查 TODO 该行状态（防止已被其它轮次误改）；  
    - 更新 working checkpoint 写清「RXX 尚未收尾」与当前进度。  

### 4.2 history 中区分任务类型

- `history.txt` 中的「类型」字段建议约定若干标签：  
  - `规划 / 设计 / 探测 / 冲浪 / 产出 / 实验` 等。  
- 如未来 history 中也记录定时任务，可采用不同前缀或单独文件，以免混淆：  
  - 例如：  
    - 自主：`R10 | ... | 产出 | ...`  
    - 定时：`S01 | ... | daily-08:00 | ...`（此处仅为示例，当前实现中还未引入）。  

## 5. 建议的协同「心智模型」

1. **定时任务是时钟驱动，自主任务是空档填充**。  
2. 遇到 scheduler 下发任务时：**一切以定时任务为先**。  
3. 自主任务的目标是「让未来的定时任务更好执行」：  
   - 设计结构（如论文追踪表、教案目录）；  
   - 探索站点/工具边界（如 arXiv / OpenReview 访问特性）；  
   - 整理 SOP 或模板，为定时重复任务提供可复用资产。  

## 6. 后续可改进点

1. **在 history 中显式区分「A: 自主」与「S: 定时」**  
   - 便于后续分析时间分配和效果。  

2. **为 scheduler 引入「占用窗口」概念**  
   - 在某些长时交互任务期间（如大型教案生成），可由 prompt 声明「当前时段不适合触发新定时任务」，避免过载。  

3. **增加冲突检测提示**  
   - 若定时任务与自主任务同时要求写同一文件或目录（极少数情况），应优先在报告中写为「待用户决策」，而不是自行覆盖。  

4. **将本草案纳入 memory 后续迭代**  
   - 当前草案放在 R10 报告中，后续如多次验证可在用户审查后写入 `../memory` 下相应 SOP 或补充说明。
