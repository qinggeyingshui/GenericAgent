# R11：适合自动抓取的学术站点调研

任务：在不触发强风控的前提下，探索比 Google Scholar 更友好的学术站点（如 arXiv、OpenReview），记录访问特性与限制，为后续自动化做准备。

本轮主要比较了 **OpenReview** 与 **arXiv**，结合浏览器实际页面结构，评估其对自动抓取的友好程度。

---

## 1. OpenReview（https://openreview.net/）

### 1.1 页面结构与内容概览

使用浏览器访问首页，当前 URL 与标题为：

- URL：`https://openreview.net/`
- Title：`Venues | OpenReview`

通过在页面中执行 JS 读取 `document.body.innerText` 片段，主体内容包含：

- 标头文案：  
  - “OpenReview.net”  
  - “Open Peer Review. Open Publishing. Open Access. Donate”
- 顶部导航/功能：  
  - “Login” 登录入口  
  - “News” 区块（包括若干条按日期排列的新闻）：
    - “OpenReview Introduces Multi-Factor Authentication for All Users” (Mar 23, 2026)
    - “Survey Finds Broad Support for Greater Openness in AI Peer Review” (Feb 13, 2026)
    - ...
    - “View all OpenReview news”
- 主体列表：
  - “Active Venues”：展示当前活跃的期刊/会议等 venue，例如：
    - TMLR、Computo、DMLR、NetSciX 2026、ACML 2025 Journal Track 等
    - 有“Show all 721 venues”链接，说明存在大量 venue，可分页或进一步浏览
  - “Open for Submissions”：显示当前开放投稿的 venue，如某些 2026 年的会议/研讨会，并注明截止时间（含时区、如 China Standard Time）

导航结构方面，DOM 抽样显示：

- 存在 `<nav class="navbar navbar-inverse">` 等导航栏元素
- 顶部导航较标准，包含登录、搜索/导航入口

### 1.2 技术特征与可抓取性

从 JS 探测结果：

- `isSPA: true`  
  - OpenReview 使用单页应用（SPA）架构，借助 `history.pushState` 等机制管理路由。
  - 很多内容通过前端 JS 及 API 动态加载，而不是静态 HTML 一次性呈现。

综合判断：

1. **URL 与路由**  
   - 首页 URL 较简单，但真正的论文列表、review、submission 等多在深层路由。
   - 具体检索页面（如某 venue 的 submissions 列表）通常通过前端路由和 API 加载。
   - 直接用 HTTP 客户端抓 HTML 可能拿不到完整数据（需要执行 JS 或调用内部 API）。

2. **HTML 结构稳定性**  
   - 顶部导航、venue 列表等结构相对稳定，但关键数据（如论文列表项、元信息）依赖 JS 渲染。
   - 站点更新时可能变动前端组件和 class 名，对纯 selector 抓取的鲁棒性有一定挑战。

3. **访问与风控推测（非侵入性）**  
   - 有正式登录体系与用户账户；部分操作需要登录（如提交评审、评论）。
   - 作为重要学术评价平台，其 API 和前端请求很可能有一定频率限制；高频无头抓取有潜在触发风控的风险。
   - 但从“公开开放”的定位来看，更可能鼓励使用其官方/半官方数据访问接口，而非简单 HTML 爬取。

### 1.3 对后续自动化的建议（OpenReview）

- **优点**  
  - 结构化 venue 视图清晰，按 venue 组织的投稿/评审流程强。
  - 许多信息理论上可以通过结构化方式访问（API/JSON），比从 Google Scholar“解析页面”更语义化。

- **局限**  
  - 单页应用（SPA）+ 前端渲染，意味着：
    - 需要浏览器自动化或直接调用内部 API（需仔细遵守使用条款），而不是简单 requests + BeautifulSoup。
    - 解析复杂度和维护成本高于简单静态页面。

- **适合作为自动抓取目标的场景**  
  - 针对**特定会议/期刊 venue**的投稿与评审信息调研：  
    可以围绕单一 venue 的 submissions / accepted papers / reviews 做精细抓取。
  - 不适合作为“统一跨 venue 的大规模论文搜索入口”来广泛爬取，尤其是匿名/高频抓取。

## 2. arXiv（https://arxiv.org）

### 2.1 搜索页结构与内容概览

使用浏览器访问 GNN 查询的搜索页：

- URL：  
  `https://arxiv.org/search/?query=%22graph+neural+network%22&searchtype=all&abstracts=show&order=-announced_date_first&size=50`
- Title：`Search | arXiv e-print repository`

JS 抽取的正文样本显示：

- 顶部区域：
  - “Skip to main content”
  - 感谢支持声明（Simons Foundation 等）
  - 顶部工具：  
    - “Help | Advanced Search”  
    - 搜索字段说明：All fields, Title, Author, Abstract, Comments, Journal reference, ...  
    - “Search” 按钮、“Login” 链接
- 搜索结果信息：
  - “Showing 1–50 of 11,111 results for all: "graph neural network"”
  - Search 版本信息：“Search v0.5.6 released 2020-02-24”
  - 显示/隐藏摘要选项： “Show abstracts / Hide abstracts”
  - 分页控制：
    - 结果数选择：25 / 50 / 100 / 200 results per page
    - 排序选项：  
      - Announcement date (newest first) 等

搜索结果 DOM 抽样：

- `li.arxiv-result`：每条结果一个 `<li>`，结构化良好：
  - ID 与链接：
    - `p.list-title a`，例：  
      - `arXiv:2603.22244` → `https://arxiv.org/abs/2603.22244`
  - 标题：
    - `p.title`，例：  
      - “Probing the Spacetime Structure of Entanglement in Monitored Quantum Circuits with Graph Neural Networks”
  - 作者：
    - `p.authors`，文本包含 “Authors: ...”

本次采样统计：

- `resultCount`: 50 （与 URL 参数 `size=50` 一致）
- 前 3 条结果均成功读取到 id / href / title / authors。

### 2.2 技术特征与可抓取性

从 JS 探测结果：

- `isSPA: true`（搜索页面同样运行在具备 `history.pushState` 能力的框架中），但与经典 SPA 有所不同：
  - 核心搜索结果列表 **以标准 HTML 列表 + 语义化标签呈现**。
  - 在传统 requests + HTML 解析场景下，也能拿到完整内容（不完全依赖前端异步渲染）。

综合判断：

1. **URL 与分页控制**（非常友好）

- 查询参数包含：
  - `query=`：搜索字符串，可精确控制并进行 URL 级别复现。
  - `searchtype=`：如 all/title/author 等。
  - `abstracts=`：show/hide 摘要。
  - `order=`：排序方式（如 `-announced_date_first`）。
  - `size=`：每页结果数（25/50/100/200）。
- 通过简单改写 URL 参数即可：
  - 变更关键词、调整排序、改变每页条数。
  - 稳定复现同一查询结果，便于分批抓取。

2. **HTML 结构稳定、语义化强**

- 每条结果为 `li.arxiv-result`，内部子元素用途明确：
  - `p.list-title a` → arXiv ID + `/abs` 链接
  - `p.title` → 标题
  - `p.authors` → 作者列表
  - 其他字段（日期、subject categories、comments 等）也有相对固定的标签与 class。
- 对于自动化抓取：
  - 可以简单用 CSS selector 抽取所需元信息，不强依赖 JS。
  - 即便前端升级，arXiv 一般会保持较好的向后兼容性和可解析性。

3. **访问与风控**

- arXiv 是开放预印本仓库，长期鼓励程序化访问：
  - 官方有 RSS feed 和 API（包括 OAI-PMH、RSS 等形式）。
  - HTML 抓取在合理频率下通常不会立刻触发强风控。
- 但依然应遵守：
  - 合理的请求速率与间隔，不进行高并发、无缓存的全库爬取。
  - 尊重 robots.txt 与使用条款。

### 2.3 对后续自动化的建议（arXiv）

- **非常适合作为“自动抓取样本站点”**：
  - 清晰的 URL 参数与分页机制。
  - 语义化、稳定的 HTML 结果列表。
  - `/abs` 页面进一步提供摘要、分类、链接到 PDF 等信息。
- 与 Google Scholar 相比：
  - Google Scholar 有更激进的反爬和验证码机制，且页面结构变动频繁、不公开 API。
  - arXiv 更开放、结构更规整、适合构建长期稳定的自动论文追踪系统。

- 可行的自动化策略：
  - 以搜索 URL 为入口，分批抓取（按页/按日期区间）。
  - 将抽取字段映射到本地追踪表（如 ID、title、authors、year、subject、link、status）。
  - 必要时配合官方 API 补充 metadata。

## 3. 与 Google Scholar 的相对比较（定性）

从“适合自动抓取”的角度（而非内容覆盖）：

- **Google Scholar**：
  - 优点：覆盖广，聚合多源引用信息。
  - 缺点：
    - 强风控：频繁访问易导致 CAPTCHA 或临时封禁。
    - HTML 结构复杂且变动频繁。
    - 无正式公开的标准化内容 API。

- **OpenReview**：
  - 优点：
    - 资料结构化、语义清晰，按 venue 组织评审流程。
    - 面向“开放评审”，有较强的透明度。
  - 缺点：
    - 强 JS / SPA 架构，很多数据不在初始 HTML 内。
    - 需要更复杂的浏览器自动化或 API 调用，维护成本较高。
  - 适合作为：**特定会议/期刊的深入分析平台**，而非通用的广覆盖抓取源。

- **arXiv**：
  - 优点：
    - HTML 和 URL 结构简单、稳定、参数化良好。
    - 对程序化访问相对友好，有官方支持方式（RSS、API 等）。
    - 结果列表语义标签清晰，抓取逻辑透明。
  - 缺点：
    - 主要是预印本仓库，范围局限于 arXiv 范围；不含所有期刊版本和引用信息。
  - 适合作为：**自动化论文跟踪与主题检索的主力数据源**，尤其是某些领域（CS、Math、Physics）的最新研究。

## 4. 结论与后续建议

### 4.1 站点选择结论（针对本任务）

在“比 Google Scholar 更适合自动抓取”的目标下：

1. **arXiv：强烈推荐**  
   - 适合作为后续自动抓取管线的首选站点。
   - 可围绕特定主题（如 Graph Neural Networks）建立长期追踪任务。
   - 推荐优先探索：
     - 搜索结果批量抓取（按 size、page 和日期切分）。
     - `/abs` 页面解析与本地元数据结构映射。
     - 合理速率控制与错误重试机制。

2. **OpenReview：有潜力但需更重工程投入**  
   - 适合在后续阶段，针对特定顶会 venue 做“深挖”：投稿、评审意见、决策过程等。
   - 抓取方式应更多依赖：
     - 浏览器自动化（类似当前 web_execute_js 一类工具）。
     - 官方/公开 API（如存在），并在报告中明确使用条款与限制。
   - 不建议将其作为“通用大规模论文抓取入口”。

3. **Google Scholar：不建议作为抓取主源**  
   - 更适合作为人工或半自动的查重与引用查看；自动化层面应谨慎，以免频繁触发风控。

### 4.2 后续可执行方向（供后续 RXX 任务使用）

- 在 arXiv 上：
  - 设计并实现一个小型“主题追踪”脚本：
    - 输入：检索式（如 `"graph neural network"`）、时间范围、更新频率。
    - 输出：结构化记录（id、title、authors、primary category、date 等），存为 Markdown/CSV/JSON。
  - 探索官方 API 或 RSS 与 HTML 抓取的组合策略。

- 在 OpenReview 上：
  - 选定 1–2 个目标 venue（例如 NeurIPS、ICLR 某年的主会/Workshop），分析其 submissions / accepted papers 页面结构及 API 请求模式。
  - 评估在不登录或只使用匿名访问前提下，能获取的公开信息范围与抓取稳定性。
